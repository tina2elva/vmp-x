# vmp-x 强度自评（决定“要不要上硬件狗”的依据）

> 口径：只写**有实测证据**的能力，和**明确挡不住**的东西。目的是让产品决策有依据，
> 而不是给出一句“很安全”。所有证据都能在 `docs/STATUS.md` 对应编号里复现。

## 一、已经做到的（每条都有对应实测）

| 能力 | 证据（如何复现） |
|---|---|
| 字节码**逐条**流式解密，明文只以“寄存器里的一个字节”存在 | `tools/residue_probe.py`：内存里搜不到字节码明文；e2e 全绿 |
| 被保护函数的**原函数体**在文件与内存里都搜不到 | residue probe 的原生代码模式搜索（`--fail-on-native`） |
| 原镜像整体加密（`.text/.rdata/.data`），入口前自解密 | e2e + image residue 检查 |
| 自哈希 + 入口蹦床校验 + **入口补丁 MAC**：回填入口字节会被拒 | `tools/patch_refill.py` + e2e（实测 `0xC000001D`） |
| 反调试四路径 + 失败**静默延后**（不是崩点） | `tools/antidebug_flag_test.py` + e2e |
| 主密钥外置：产物里**搜不到**主密钥（真密钥 0 处；兼容模式对照 2 处） | e2e 的 1b 用例 + 原始字节搜索 |
| 每条目 KDF、带密钥 MAC（Poly1305）、容器字段混淆、ASLR/重定位保留 | `STATUS #383/#386/#387/#390` 各自的 KAT 与 e2e |

## 二、明确挡不住的（必须写进商务沟通口径）

1. **运行期内存抓取 / 调试**：密钥在执行期必然出现在进程里。反调试提高成本，但**不是硬件隔离** ——
   这正是“上硬件狗”要解决的问题（密钥留在狗里，进程里只有中间结果）。
2. **用户态校验可被 patch**：自哈希 + MAC + 多路径反调试把成本抬高，但**不是不可破**（专业团队能改）。
3. **VM 字节码本质是原函数的“提升”**：一旦有人 dump 出解码后的指令流，函数语义就回去了。
   这是**所有 VM 型保护的通病**（Themida/VMProtect 同样如此），不是本项目的特例。
4. **没有白盒密码学**：不防有充足时间的专业逆向 + 手工重建。

## 三、结论（对商业化意味着什么）

- 对**随手破解、静态分析、直接 dump 即用**这类攻击：vmp-x 把成本抬得很高（这是“有没有商业化价值”的分水岭）；
- 对**有充足时间、有专职逆向**的攻击：挡不住。所以商业价值不应建立在“代码不可逆”上，
  而应建立在**授权与密钥托管**上 —— 让“能不能跑”由授权层决定（Sentinel 狗 或 我们签名的授权文件），
  让“代码语义”由 vmp-x 保护。
- **两者是叠加关系，不是二选一**：
  - 已具备 Sentinel 母狗/子狗：可以让 vmp-x 的密钥/授权来自狗（密钥不出狗），破解者要同时攻破 VM 与狗；
  - 暂不上狗：用已交付的**签名授权**（Ed25519，`vmpepoch lic-*`）做“可增删、可到期、不可伪造”的授权，
    代价是授权文件可复制（无硬件绑定）、到期可被改系统时间绕过（需机器绑定/联网校时配合）。
- 一句话给销售：**“能显著抬高破解成本，并把授权做成可管理、可撤销的东西”** —— 不要承诺“不可破解”。
## 四、工具自身的授权控制：为什么「建议做」，以及 Sentinel 的壁垒在哪

### 4.1 先纠正一句话

上一轮我说工具授权「可做可不做」，那是**工程口径**（不做也能跑起来），**不是商业建议** ✗。
商业上：**卖工具却不做任何授权控制 = 卖一次就没了**，因为一份拷贝可以服务无限客户。

### 4.2 但「给工具加壳」不是第一选择

加壳只提高**逆向成本**，而授权的本质是**控制谁能用**。更有效的是把「使用工具的权利」
绑到**你签发的身份**上 —— 这正是 Sentinel 的做法（见 4.3）。

### 4.3 Sentinel 的壁垒到底是什么（不是「加密更牛」）

| 壁垒 | 说明 | 能不能用软件近似 |
|---|---|---|
| **硬件密钥隔离** | 密钥/授权在防拆芯片里，**不进进程** → 攻击从 dump 内存变成开盖/侧信道，成本差几个量级 | 部分：**TPM/CNG 不可导出密钥** ✓（性价比最高的一步） |
| **狗参与解密** | 应用的解密依赖狗（hasp_decrypt / 狗内 AES）→ 拷授权文件没用、没狗跑不了 | 弱：纯软件只能靠机器绑定近似 |
| **工具授权 = 客户身份（母狗）** | 没 Developer key 用不了 Envelope、没 Master key 发不了授权 → **卖工具这件事本身被硬件锁住** ✓✓ | **能，而且值得学**：工具启动校验「你签发的构建凭据」 |
| **授权生命周期基础设施** | EMS：签发/更新/到期/回收/网络授权/虚拟化支持 | 大部分能：证书链/委派/到期我们已有；**吊销/在线**还没有 |
| **品牌 + 合同 + 支持 + 责任** | 大客户买的是「可持续 + 有人负责」，不是「不可破」 | 商业层，代码替代不了 |
| **30 年攻防积累** | 知道攻击者会怎么打，持续更新 | 时间换不来，只能持续投入 |

**结论**：Sentinel 不是「不可破」，它是 **「密钥不在软件里 + 工具授权绑硬件身份 + 一整套授权生命周期 + 品牌责任」**。
他们的加密值得尊重，但**壁垒主要是系统工程 + 商业信任**，不是某个算法。

### 4.4 对 vmp-x 的建议（按性价比排序）

1. **工具授权绑身份**（强烈建议，用已有积木 1–2 天）：`vmpbuild/vmpack` 启动时校验一份**由你的根签发的构建凭据**
   （含 vendorID / 到期 / 能力位），并**只允许用该凭据里的 vendorID 构建**。转卖工具的人拿不到你签的凭据 ✗。
2. **构建凭据绑机器**（TPM / 机器指纹）：让一份凭据不能到处用 ✓。
3. **要硬件级**：直接上 Sentinel（你们已有母狗/子狗）—— 把「工具使用」绑到 Developer/Master key，
   白拿硬件密钥隔离 + 狗参与解密 ✓。此时我们的 PKI 只需做**接口层**。
4. **商务层**：合同 + 更新/支持绑定。很多转卖问题在合同层就解决了，技术只是最后一道。
5. 可选：用 vmp-x 给工具**加壳**（注意自举顺序：用冻结的旧 blob 保护新工具，链式不循环）。
**工具授权（构建凭据）已实现 —— 对应 4.4 的第 1 条**

```
# 客户侧：自己生成「工具安装密钥对」，并把公钥（带持有证明）交给厂商
vmpepoch keygen   --out vmpx
vmpepoch cert-req --key vmpx.priv --vendor ACME-0001 --out vmpx.req.json
# 厂商侧：签发构建凭据（有效期/备注；可绑机器指纹，预留）
vmpepoch cred-issue --root root.priv --req vmpx.req.json --vendor ACME-0001 --until 2028-12-31 --out vmpx.cred
vmpepoch cred-show  --cred vmpx.cred --root root.pub
# 部署：把 vmpx.cred 与私钥（命名为 vmpx.key）放到 vmpbuild/vmpack 同目录；或用 -cred / $VMPX_CRED
```

**工具侧**：厂商根公钥**烘进工具二进制**（发布构建）：
`go build -ldflags "-X github.com/vmpx/vmp-x/internal/cred.RootPubHex=<64字节hex>"`。
留空 = 开发构建 → 校验关闭（只打一行提示），因此现有 CI/gates 不受影响 ✓。
校验内容：签名 → canBuild → 有效期 → **vendorID 与本次构建声明一致** → 本机私钥与凭据绑定公钥配对。
不通过一律 exit 8，并打印原因。

**实测（本机，六种情形）**：凭据不在 → 拒；凭据在但私钥不在 → 拒（**只拷 .cred 拷不走权限**）；
凭据+私钥齐全 → 通过；`-vendor` 与凭据不一致 → 拒；凭据过期 → 拒；凭据被改一个字段 → 拒（签名失败）；
恢复后重跑 → 通过 ✓。

**边界（如实登记）**：
- 这只防「顺手转卖/复制工具」✓；铁了心 patch 工具的人仍然能绕过（与所有软件许可同一边界）✗；
- 机器绑定是**预留**（`--machine` + `machineID()` 现在返回空 = 不校验），接 TPM/机器指纹时在那里实现；
- 私钥目前是明文文件 `vmpx.key`，下一步应改为 **DPAPI/TPM 不可导出**（否则复制私钥同样绕过）。


### 4.5 一句话给销售

> 我们的价值不是「不可破解」，而是 **「把破解成本抬到不划算 + 让授权可管理、可撤销、可追责」**；
> 对客户来说，**可持续的更新与有人负责**，比二进制不可读更重要。
