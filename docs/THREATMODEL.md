# THREATMODEL —— 抗"有狗客户脱壳再分发"的目标与当前不足

> 这份文档记录**威胁模型、目标、以及 vmp-x 当前已核实的能力与不足**。
> 所有"不足"都带 `文件:行` 依据（本轮实际读过代码），不是推测。

## 1. 威胁模型（客户给定）

- **对手**：能在目标机上**运行/调试**的人；他**持有合法的外置 HL（加密锁）**（试用或购买）。
- **攻击路径**：用合法狗跑起来 -> 取密钥 / 仿真狗 -> 产出一个**不需要狗**的版本 -> **分发**。
- **目标**：让他**拿不到可运行的等价体**（尤其是可分发的那一份）。

## 2. 诚实的结论（先说清楚天花板）

1. **"绝对拿不回可运行等价体"做不到**：任何能在他机器上运行的东西都能被 dump 与重组，
   差别只是**要花多少人月**。
2. 因此正确目标有两条、且都**可验收**：
   - **(T-a) 不可移植**：产物 + 狗搬走就不能跑（对手必须做出**通用**破解，而不是拷一份内存镜像）；
   - **(T-b) 成本高于授权价**：让"做出一份可不带狗分发的版本"的成本明显高于一份授权，
     并让**一次破解不能长期通吃**所有客户与版本。
3. **不要对外承诺**"不可脱壳/不可破解"；可承诺的是"狗绑定 + 高强度反分析 + 每客户唯一构建 + 可吊销"。

## 3. 当前**已核实**的能力（不是不足，先摆出来）

| 能力 | 依据 |
|---|---|
| 被保护函数的原生指令不在产物里（`-wipe`） | 门禁 `residue probe`（磁盘与内存都搜 native code） |
| 字节码**永不整份明文**：取指时按 64 字节块现推密钥流、逐字节 XOR | `vmb_byte`；门禁 `bytecode plaintext scan` |
| 镜像整体加密（AEAD，按节一把派生密钥，nonce 绑 rva/size/salt） | `vm_interp.c:2940-2948`；门禁 `image residue` |
| 运行期取钥接缝：**文件 -> 环境变量**，或 **严格模式只用狗**（`kind>=2`） | `vm_interp.c:1251-1262` |
| **狗取钥是真实现**（动态加载 DLL、login/read、分阶段失败码 `vm_sentinel_fail_stage`） | `vm_interp.c:1184-1224` |
| **任何解密之前**先做 KCV 自检；失败统一硬门 **`0xC0DE0007`**、无输出 | `vm_interp.c:1263-1269`、`:961` |
| 防篡改：自哈希 `vm_selfcheck`、入口补丁 MAC、KCV | `vm_interp.c` 多处 |
| 反调试 4 条路径（PEB / NtQueryInformationProcess / 调试寄存器 / 时间差），命中**静默给错结果** | `vm_antidebug` |
| 构建期可直接从狗取主密钥：`-key-in dongle:<fileID>:<offset>:<length>` | `cmd/vmpbuild/main.go:480-494` |

## 4. 当前**不足**（按对本威胁模型的影响排序，均带依据）

### G1（最大）镜像解密是"整节解密到内存"，dump 一次即得明文节
- `vm_interp.c:2940-2948`：按节 `dst = base + rva`，一次解密整节。
- 影响：持狗者跑一次、dump 内存，即得到**明文镜像**；虽然被保护函数位置是 `E9` 跳转（原文已被 wipe），
  **镜像其余部分**是明文。
- 对策：**按页惰性解密 + 用完回写**（不依赖任何新硬件，可立即开工）。

### G2 默认模式把主密钥编进 blob
- `vm_interp.c:761`："兼容模式（默认）：blob 里就带主密钥"。
- 影响：默认产物对"拿到文件的人"没有密钥门槛；有狗者更容易走到 G1。
- 注：外置模式**已存在**（`-key-external`），只是下面 G3 限制了它的适用范围。

### G3 外置密钥模式只支持 win/x64
- `cmd/vmpbuild/main.go:150`：`if *keyExternal && targetRel != "win/x64"` => 仅 win/x64。
- 影响：**i386 / Linux / arm64 没有外置密钥**，也就没有机器/狗绑定。

### G4 i386 没有镜像整体加密
- `cmd/vmpack/main.go:571-572`：`原镜像整体加密目前只支持 x86-64 / arm64（i386 先跳过这一项）`。
- 影响：32 位产物只有"VM 化 + wipe + 字节码加密"，整体保护少一层。

### G5 无吊销 / 无 features 语义
- `docs/TODO.md:474`（吊销/黑名单未做）、`:598`（`features` 语义未实现）。
- 影响：**一次破解可长期通吃**；无法按功能点或按客户收紧。

### G6 缺"狗参与密码学"的用法（只把狗当取钥/校验点）
- 已存在的 `vm_key_from_sentinel()` 是**取主密钥**；TODO `:596` 的路线 A（`hasp_login`/`hasp_get_info`/`hasp_decrypt`）尚未落地。
- 影响：对手**仿真狗**或**记录-重放**即可绕过（他本来就有狗）。
- 对策：让关键解密**必须经过狗内部非导出密钥**，并把会话/狗身份绑进密钥派生。

### G7 机器/狗绑定的其余形态未做
- `docs/TODO.md:225`（TPM/TEE/授权回调封印）、`:599`（母狗私钥保护 + `vmpbuild --key-from-dongle`）。
- 注：DPAPI **工具侧已有**（`cmd/vmpepoch/license.go:130` 给签名私钥用）；**payload 主密钥**的受保护形态
  已在 `STATUS #590` 落地 —— `<产物>.vmpkey.dpapi`（`cmd/vmpkeywrap` 生成，运行期优先读它，
  用 crypt32 的 `CryptUnprotectData` 解）。要点：它挡的是"拷走密钥文件到别的机器/别的用户"，
  **不挡**同一用户在本机解密，也不防内存抓取；要更强仍得上 TPM/TEE。
- **本轮进展（t1，`<产物>.vmpkey.ncrypt` 已落地）**：主密钥改用本机 **CNG 持久化 RSA-2048 的公钥**包裹
  （优先 Microsoft Platform Crypto Provider = TPM，不可用则退软件 KSP），运行期由 blob 自己调
  `NCryptOpenKey`+`NCryptDecrypt` 解出 32 字节，私钥永不以可用形式存在。运行期优先级
  **`.ncrypt` > `.dpapi` > 明文**，任何一步解不开就按序回退（既有部署逐字节不变）。
  本机实测 **TPM 2.0 路径端到端通过**（`tpmtool getdeviceinformation` 报 TPM 2.0 / INTC / 固件
  700.19.18.2595；wrap 密钥落在 `%LOCALAPPDATA%\Microsoft\Crypto\PCPKSP\<guid>\*.PCPKEY`，
  而 `-provider software` 的密钥落在 `%APPDATA%\Microsoft\Crypto\Keys`，是两套不同存储）。
  **未验证**的是"硬件保证本身"（私钥物理上无法离开芯片）：Platform Crypto Provider 不支持
  `Impl Type` 查询（返回 0x80090029）⇒ 没有 impl-type/证明级别的证据。
  ⇒ 到本轮为止，"主密钥不落地 + 绑本机"已有 **L2.5 档**（强于 L2、弱于 L3 的 TPM 封印）落地；
  G7 里只剩 **① 授权回调形态** 与 **② TEE/远程证明那一档**。

#### G7-1b「授权回调取钥」形态：ABI 与威胁模型（本轮只定设计，不改任何格式）

> 记录的是**设计决定**（含否掉的备选），不是新的缺陷。原始登记见 `docs/TODO.md:19/225`、
> `docs/HANDOFF.md:85`（"真主密钥来源可切：env / 外部文件 / 授权回调"）。

**结论：默认不做（与 `docs/TODO.md:19` 的"可砍"一致）；只有「条件 GO」三条同时成立时才按本节 ABI 实现。**

一句话理由：**这个形态本身不是安全边界** —— 它只是把"密钥从哪来"外包给宿主。宿主没有更强信任锚时，
它相对已落地的 `.dpapi`/`.ncrypt` 是**降级**：那两档至少保住"产物连同密钥文件拷到别的机器/别的用户就不能跑"，
而回调形态的绑定强度**等于宿主自身的绑定强度**（宿主能跑的地方，回调就能跑）。

**条件 GO（三条同时成立才实现）**
1. 交付形态是 **DLL 产物 + 宿主 EXE**（EXE 产物没有独立宿主，pull 会退化成"自己找自己"）；
2. 宿主的回调有**不弱于 `.ncrypt` 的锚**（TPM/CNG、服务端签发、或宿主自己的强绑定）；
3. 客户接受 fail-closed 的代价：宿主没给回调时**产物直接杀掉宿主进程**（`0xC0DE0007`、无输出）。

若不做，替代方案就是已落地的两档：`<产物>.vmpkey.dpapi`（用户作用域、运维零成本）与
`<产物>.vmpkey.ncrypt`（TPM/CNG 绑定，本机可验）。"磁盘上不留可用密钥"这一目标 `.ncrypt` 已达成；
"密钥物理上不出芯片"属于 TEE/证明那一档（G7 的另一半，仍未做）。

**Q1 谁调用谁：产物 pull（在宿主模块里按导出名找）；否掉 push**
- **选定 pull**：产物在需要主密钥的那一刻，从 PEB 模块表定位宿主模块（默认 = 主镜像
  `PEB->ImageBaseAddress`，也可烘一个模块名），用现成的 `vm_find_module` + `vm_get_proc`
  （`vm_interp.c:3519` / `:3654`，已含转发导出处理）取导出地址并调用。
- **否掉 push**（宿主调产物导出的 `vmpx_set_key`，理由两条）：
  1. **时序不成立**：密钥必须在**第一次 `vm_run` 之前**就位，而最早的取钥点是入口蹦床
     `vm_verify_table()`（`vm_interp.c:3122` → `:3127` 先 `vm_master()`）—— 它还在 **`main` 之前**；
     DLL 形态下更是 `DllMain`/加载期。对"加载期导入的 DLL 产物"，宿主的 `main` 与 CRT 初始化
     **都还没跑**，**加载器不保证**宿主的初始化器先于产物的 DllMain 执行 ⇒ 宿主没有一个可靠的"先 push"时机。
  2. push 要求产物**导出**符号（EXE 导出不常见，且等于给对手一个现成调用点），并给宿主增加一个必须调对的 API 面。
- pull 的代价：产物要知道"哪个模块、哪个导出名"（见 Q3）；回调必须能在早期上下文里安全执行（见 Q2 约束）。
- 怎么找模块：`<export>`（无模块名）= **主镜像** `PEB->ImageBaseAddress`
  （x64 偏移 +0x10 / x86 +0x08；**本文件目前没有这个常量**，实现时要加两行）；
  `<module>!<export>` = 按名字在 PEB 模块表里找（适合宿主是启动器/外壳/另一个 DLL）。EXE 产物用第一种没有意义（条件 GO 第 1 条）。
- **重要性质：模块解析被劫持只会 fail-closed，不会泄露密钥。** 对手塞一个同名模块顶替回调，
  他**提供**的密钥必须能过 KCV —— 而那要求他**已经知道**密钥。所以被劫持的后果是"拒绝运行"，
  不是"拿到密钥"。
- **一并否掉**的其它传钥通道：命名共享内存/命名管道/注册表（要更多 OS 面与生命周期/ACL 语义，强度不增，
  第三方还能按名字打开）；运行期环境变量（就是现有 `kind=0` 的 `VMPX_KEY`，密钥进子进程环境块，更弱）。

**Q2 ABI：签名、调用时机、fail-closed**
- 签名（v1，C ABI；导出名按**名字**导出，不用序号）：
  ```c
  /* 宿主导出：把 32 字节 payload 主密钥写进 out，返回写入的字节数。 */
  int __stdcall vmpx_key_cb(unsigned char *out, unsigned int outLen);
  /*  return 32  = 成功（恰好写入 32 字节）
   *  return <=0 = 失败；其它值同样按失败处理（产物一律 fail-closed，不看具体值） */
  ```
  刻意**不带 `ctx`/`flags`**：接口一旦公开就要长期兼容，而"宿主替产物做解密"那种更丰富的接口与
  这个签名不兼容（见下面的否掉项），宁可不烘。
- **调用时机**：由 `vm_master()` 的严格分支调用（`vm_interp.c:1913` 那处 `kind>=2` 接缝），
  **每进程最多一次**（`vm_master_ok` 缓存）。最早发生点是入口蹦床 `vm_verify_table()`（`main` 之前）
  ⇒ **在任何解密与第一次 `vm_run` 之前**。
- **调用上下文（本 ABI 最容易踩的地方，必须写进宿主文档）**：`vm_master()` 会在三种上下文首次被调用 ——
  ① 入口蹦床（`main` 之前，EXE 已释放 loader lock）；② **TLS 回调**（默认 `-enc-image` 产物把自解密 thunk
  插在 TLS 回调数组第 0 项，它内部就调 `vm_master()`，见 `:3762`）—— 此时 **loader lock 被持有**；
  ③ 第一次被保护调用（最安全）。
  所以回调**必须**：不加载任何 DLL、不取 loader lock、不等锁、不做网络 I/O、不依赖 CRT/静态构造器已初始化。
  宿主若要先做重活（连服务器、解 TPM 封印），**正确姿势是：宿主 `main` 先备好密钥 → 再 `LoadLibrary`
  产物 DLL**，此时回调只剩"把 32 字节从自己的 .data 拷出去"。
  这条也说明**不能**把门禁/取钥挪到 `main` 之后 —— `:3120` 已写明"加载期检查是拦回填原生代码的唯一时机"。
- **fail-closed**（对外统一 `0xC0DE0007`、无输出；与现有硬门同一个 `vm_key_reject()`）：

  | 情况 | 结果 |
  |---|---|
  | 模块找不到 / 导出名找不到 / 名字非法 | 硬门。它属于 `kind>=2` 严格族 ⇒ **没有**"回退文件/环境变量" |
  | 回调返回值 ≠32 或 > `outLen` | 硬门 |
  | 回调给了 32 字节但密钥不对 | KCV 不过 ⇒ 硬门（与"没给"对外**无差别**：不泄露"给错了"这一位信息） |
  | 产物是 DLL | 同上；`vm_key_reject()` 走 `NtTerminateProcess` ⇒ **杀掉宿主进程**（现有严格模式就是这个语义，属预期） |

- **ABI 自检**：`vm_key_src.reserved` 当 **ABI 版本**（v1 = 1），运行期只认 1，其它值直接硬门 ——
  免得将来改了语义还在吃旧产物。
- **不烘"密钥校验和"**：KCV 已经是 **16 字节**（`cmd/vmpbuild/main.go:641` `VM_KEY_CHECK_LEN 16`）
  的密钥绑定校验；再烘一个更短的验证值只会多给对手一个预言机。反过来必须守住一条不变量：
  **任何会吃"密钥猜对了没有"这一位的检查，长度都不得短于 KCV 现状** ——
  否则"宿主可控回调 + accept/reject"就变成离线爆破预言机。

**Q3 打包端烘什么（复用现有结构，零格式变更）**
- 复用 `vm_key_src`（`vm_interp.c:1567-1576`，共 284 字节）：
  - `kind = 4`（新值；现有 0=文件/环境变量、2=真狗、3=假狗文件）；
  - `fakePath[128]`（今天只有 `kind=3` 用）填 `"<module>!<export>"`（模块名可空 = 主镜像；整串 ≤127 字节）；
  - `reserved` 填 **ABI 版本 1**；`length` 仍填 32（回调契约固定 32 字节）；其余字段保持 0。
  ⇒ **结构尺寸、字段偏移、自哈希覆盖范围都不变**，`internal/inject`、`internal/load`、manifest 一律不用动；
  `vmpack` 打完补丁照现有做法**重算自哈希**（`cmd/vmpack/main.go:181-189`，那条被 `STATUS #399` 咬过）。
- 新增开关 `vmpack -key-callback "<module>!<export>"`（**必须显式给**、无默认值），并加四条守卫：
  1. 只接受 `-key-external` 构建的 blob（沿用 `-dongle-*` 的既有守卫）；
  2. 与 `-dongle-key` / `-dongle-fake-file` **互斥**（kind 只能取一个值）；
  3. **非 Windows 目标直接拒绝**：Linux blob 的 `vm_find_module`/`vm_get_proc` 是返回 0 的桩
     （`vm_interp.c:1210-1211`）⇒ kind=4 在 Linux 上恒硬门，不能静默构建出"永远跑不起来"的产物；
  4. 打一行**显式警告**（"该形态不是安全边界：绑定强度等于宿主自身的绑定强度"），并打印 ABI 版本与导出名备查。
- 可选校验和：**不做**（理由见 Q2 末条）。

**Q4 与现有 kind 路由如何共存：并入严格族，不新增 kind 族**
- 现有分派是：`kind>=2` ⇒ 只走 `vm_key_from_sentinel()`、失败即硬门、**不回退**（`vm_interp.c:1913-1915`）。
  kind=4 只在该函数里加一个分支（把 `vm_key_from_sentinel()` 当"provider 分派器"：2=狗、3=假狗文件、4=宿主回调），
  **不给 kind=4 任何回退**，也不改 `kind=0` 的行为（默认"文件 → 环境变量"逐字节不变）。
- 与授权层**正交**：`vm_license_meta.kind`（`.vmplic.bin` 验签 / 问狗要授权）不受影响，可以同时开
  （先取钥，再在 `vm_verify_table` 里做授权门禁）。
- 失败归因：沿用 `vm_sentinel_fail_stage`，给回调路径分配新段（建议 `0x4x`：0x41 模块没找到、
  0x42 导出没找到、0x43 返回值非法、0x44 ABI 版本不符），对外仍是同一个硬门码。

**Q5 威胁模型增量（相对 `.dpapi` / `.ncrypt`）**

| 维度 | 增量 |
|---|---|
| 磁盘上的密钥形态 | **更好**：部署目录里**没有任何**密钥文件（连密文都没有）⇒ 单拿产物文件毫无用处 |
| 每台目标机的部署步骤 | **更好**：不需要在客户机上跑 `vmpkeywrap` 做机器绑定（`.ncrypt`/`.dpapi` 都必须在目标机上生成） |
| 与硬件的绑定 | **取决于宿主**：回调若只是内存里算出来/硬编码，则**完全没有**机器绑定（宿主能跑的地方产物就能跑）⇒ 相对 `.ncrypt` 是**降级**；只有回调自己以 TPM/CNG/服务端为锚时才不降级 |
| 明文密钥的位置 | **一样（不可避免）**：宿主要交出 32 字节明文，它必然出现在**宿主进程内存**里；任何形态下 `vm_master_buf` 里也都有明文 ⇒ 有调试/内核权限的对手都能在正确时刻取到。回调只是把"正确时刻"从产物侧挪到宿主侧，**不改变**这一点 |
| 对手成本 | **不增加**（对手手里本来就有宿主程序）：他可以在自己进程里 hook 这个导出、读走返回值（比破 TPM 简单得多）。他也能自己写一个"合法宿主"来喂产物 —— 但**喂不出正确密钥**（KCV 挡着）；他能做到的是"用自己的宿主把产物跑起来"，那恰恰就是他的目标 ⇒ **对 T-a（不可移植）没有帮助** |
| 可吊销性 | **不增加**：主密钥必须**每次运行都相同**（字节码密文与 KCV 都是构建期烘进去的），服务端无法换一把"短时密钥"；宿主拒绝提供只是"这台机器不跑"，老版本无法回收（与 `.dpapi`/`.ncrypt` 同） |
| 失败模式 / 支持成本 | **更差**：多一类"产物必须在特定宿主上下文里被加载"的集成约束（导出名改动、延迟加载顺序、被启动器/服务加载），踩坑表现为产物直接杀进程 |
| 密钥预言机风险 | **新增，且必须守住**：回调让对手指定输入、产物只回"对/错"；只要判据不短于 KCV（现 16 字节）就不构成可爆破的预言机 |

**否掉的备选方案**

| 备选 | 否掉的理由 |
|---|---|
| 宿主 push（产物导出 setter） | 时序不成立（见 Q1）；还给宿主加一个必须调对的 API、给对手一个现成调用点 |
| 命名共享内存 / 命名管道 / 注册表传钥 | 要引入更多 OS 面与生命周期/ACL 语义，强度不增；共享对象还能被第三方按名字打开 |
| 运行期环境变量（宿主设 `VMPX_KEY`） | 就是现有 `kind=0` 的形态；密钥进进程环境块（同用户可读），比导出调用更弱 |
| "宿主替产物做解密"（回调只回**派生密钥/密钥流**，不回主密钥） | **更强**（主密钥从不进入产物里的单一缓冲），但 ABI 与"回 32 字节"完全不兼容，且每个 64 字节字节码块都要回调一次 ⇒ 开销与改动面大一个量级。登记为"将来真要'密钥永不出现'时应重新设计的另一条线"（与 G6 的"狗参与密码学"同族），**不往 v1 里兼容** |
| 把 kind=4 也做到 Linux | Linux 没有"按名字找宿主导出"的实现（`vm_find_module` 是桩）⇒ 只会得到必然硬门的产物；要做必须另开一轮（`dl_iterate_phdr` + `dlsym`） |

## 6. 可自动化验收（建议加进门禁/CI）

1. **跨机/跨狗不运行**：产物 + 密钥/狗搬到另一环境 => 必须恰好以 `0xC0DE0007` 失败；
2. **dump 不可离线运行**：运行中 dump 内存镜像后离线启动 => 必须失败（W1 的目标）；
3. **归因**：每客户构建唯一 => 从泄漏产物能反查授权编号；
4. **可吊销**：吊销后**新版本**拒绝该客户（老版本无法回收，需如实告知客户）；
5. **成本指标**：记录"重建一个 N 条 IR 的函数所需的最少 trace 覆盖"，作为持续跟踪指标。
