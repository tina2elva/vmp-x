#### ARM64 覆盖率（第 79 轮新增，首次实测）

覆盖率工具原先只认 `EM_X86_64`，本轮补上 AArch64 分支（解码 → ARM64 lifter → 同一套统计），
并用 **Go 交叉编译**出的真实 AArch64 ELF 测到第一手数字（`GOOS=linux GOARCH=arm64 go build`）：

| 目标 | 函数级 | 指令级 |
|---|---|---|
| `build/arm64_target`（Go 编译的 AArch64 ELF，1791 函数） | **78/1791 = 4.4%** | **106908/120474 = 88.7%** |

读法（重要）：**指令级 88.7%** 说明 lifter 认得大部分 AArch64 指令；
但**函数级只有 4.4%** —— 只要函数里出现**一条**不支持的指令，整段就不算『可整段翻译』
（部分可翻译 1711 个）。Go 的 AArch64 输出里 SIMD/浮点/系统指令很常见，所以差距被放大。
x86-64 侧对比：函数级 87.7%~91.4%、指令级 99.5~99.6%。

注意事项（避免把这个数字当定论）：覆盖率工具给 ARM64 lifter 的 `ImageBase`/`FrameSkew` 都是默认值，
真实打包时这两者由符号表与 ABI 常量填；后续若要提升 ARM64 支持度，应当用真实 blob 的参数再测一遍。
#### 最关键的后续工作项（量化结论）

**ARM64 的函数级覆盖率只有 4.4%**（对比 x86-64 的 87.7~91.4%），指令级 88.7%。
也就是说：ARM64 lifter 认得大部分指令，但「一条不支持就整段不算」的规则把函数级压得很低。
要把它推到实用水平，优先补的是 Go AArch64 输出里最常见的那些：SIMD/浮点（含 MOVI/DUP/EOR/ ADD 向量形）、
以及 `MRS/MSR`、barrier、`CSEL` 之外的条件选择、部分 `LDP/STP` 变体。
（测量口径的局限见上一节末尾的注意事项。）

#### 剩余被拒指令（`build/linux_target` 的 719 条中）
x87 与浮点转换扩展、AES-NI、AVX/VEX、REP 字符串、`SYSCALL`、以及冷块/跳转表的少数形态。

## 3. ARM64：客户机语义（已达成）vs 宿主（需 CI）

**已在本机真实验证**（第 76–77 轮修好并纳入门禁）：

- `TestGuestSemanticsSwitch`：ARM64 的「无借位」语义 —— CMP 相等后 C=1，因此 **CS 跳转、CC 不跳转**（与 x86 相反）；
- `TestArm64GuestInCInterpreter`：成规模的差分 —— AArch64 指令 → lift → 字节码，分别由 Go 参考 VM 与
  **真 C 解释器**（`-DVM_GUEST_ARM64 -DVM_REG_COUNT=35`）执行，逐寄存器 + 标志位比对。

做法：用 **x86-64 宿主 blob** 承载 **arm64 客户机字节码**（`vmpbuild -guest arm64`），
因此不需要 aarch64 工具链也能验证客户机语义。命令见 `docs/RUNBOOK.md` 4.5。

**仍需 CI/真机**：ARM64 宿主 blob 构建（Windows/arm64、Linux/arm64）与 Linux/arm64 的 qemu 端到端。

## 4. 未达标项与已知问题（如实列出）

1. **解释器用 `-O1` 编译**：`-O2` 下，只要浮点函数里含**整数↔浮点转换**，**整个解释器**会被 gcc 编译错
   （连不执行浮点的 `check_key` 都算错）。已二分到触发点，但**根因未定位**（疑为解释器里既有 UB）。
   代价已实测（第 79 轮复测）：`check_key` protected **50 ns/iter**、`sum_to` **1100 ns/iter**；与 -O2 时代的 35/700 相比约 1.4–1.6×。
2. **`fp_mix` 的两个大参数**取值仍与原生不符（未定位），因此没有进 E2E 用例清单。
3. **调用约定只覆盖整数参数/返回值**（浮点/向量参数不进出宿主）；浮点只在被保护函数内部可用。
4. **ELF 共享库的运行时 `dlopen` 验证**缺失（定位逻辑已打通，需 Linux 执行）。
5. **CI 未实跑**：`ci.yml` 的四个作业都已写好并通过静态校对（路径存在性、`bash -n`），但从未真正运行过。
6. `docs/STATUS.md` 的**第 52–57 轮条目已丢失**（我在第 75 轮做整文件重排时被读取上限截断所致），
   第 58–75 轮只有要点补记；完整细节仍在会话记录中。

## 5. 怎么把 ⑤ 真正闭环（建议路径）

1. 把 `D:\vmp-x` 推到一个 GitHub 仓库（目前**不是 git 仓库**，也没有 `.gitignore`→ 已补上）；
2. 启用 `.github/workflows/ci.yml`，四个作业会分别回答：
   - `windows-amd64`：x86-64 E2E（146 例）+ DLL E2E（3 例）—— 预期通过；
   - `linux-amd64`：`tools/e2e.sh`（含「不得有 W+X 段」断言）—— **首次运行最可能暴露问题**（脚本从未在 Linux 上跑过）；
   - `linux-arm64`：`tools/e2e_arm64.sh`（aarch64 交叉工具链 + qemu-user）—— 同样首次运行；
   - `arm64-guest-differential`：ARM64 客户机语义（本机已通过；CI 侧用的是 linux/amd64 宿主 stub 的等价配方，尚未实跑）；
   - `windows-arm64-blob`：Windows/arm64 blob 构建 —— 需要一个能产出 aarch64 **COFF** 的编译器，CI 镜像可能没有；
     该作业会**明确失败**并指出缺哪个工具（设计上不允许静默跳过）。
3. 把 CI 的真实输出贴回来，我按结果修（这是唯一能闭环 ⑤ 的方式）。
