#### ARM64 覆盖率（第 79 轮新增，首次实测）

覆盖率工具原先只认 `EM_X86_64`，本轮补上 AArch64 分支（解码 → ARM64 lifter → 同一套统计），
并用 **Go 交叉编译**出的真实 AArch64 ELF 测到第一手数字（`GOOS=linux GOARCH=arm64 go build`）：

| 目标 | 函数级 | 指令级 |
|---|---|---|
| `build/arm64_target`（Go 编译的 AArch64 ELF，1791 函数） | **78/1791 = 4.4%** | **106908/120474 = 88.7%** |

读法（重要）：**指令级 88.7%** 说明 lifter 认得大部分 AArch64 指令；
但**函数级只有 4.4%** —— 只要函数里出现**一条**不支持的指令，整段就不算『可整段翻译』
（部分可翻译 1711 个）。Go 的 AArch64 输出里 SIMD/浮点/系统指令很常见，所以差距被放大。
x86-64 侧对比：函数级 87.7%~91.4%、指令级 99.5~99.6%。

注意事项（避免把这个数字当定论）：覆盖率工具给 ARM64 lifter 的 `ImageBase`/`FrameSkew` 都是默认值，
真实打包时这两者由符号表与 ABI 常量填；后续若要提升 ARM64 支持度，应当用真实 blob 的参数再测一遍。
#### 最关键的后续工作项（量化结论）

**ARM64 的函数级覆盖率只有 4.4%**（对比 x86-64 的 87.7~91.4%），指令级 88.7%。
也就是说：ARM64 lifter 认得大部分指令，但「一条不支持就整段不算」的规则把函数级压得很低。
要把它推到实用水平，优先补的是 Go AArch64 输出里最常见的那些：SIMD/浮点（含 MOVI/DUP/EOR/ ADD 向量形）、
以及 `MRS/MSR`、barrier、`CSEL` 之外的条件选择、部分 `LDP/STP` 变体。
（测量口径的局限见上一节末尾的注意事项。）

#### 剩余被拒指令（`build/linux_target` 的 719 条中）
x87 与浮点转换扩展、AES-NI、AVX/VEX、REP 字符串、`SYSCALL`、以及冷块/跳转表的少数形态。

## 3. ARM64：客户机语义（已达成）vs 宿主（需 CI）

**已在本机真实验证**（第 76–77 轮修好并纳入门禁）：

- `TestGuestSemanticsSwitch`：ARM64 的「无借位」语义 —— CMP 相等后 C=1，因此 **CS 跳转、CC 不跳转**（与 x86 相反）；
- `TestArm64GuestInCInterpreter`：成规模的差分 —— AArch64 指令 → lift → 字节码，分别由 Go 参考 VM 与
  **真 C 解释器**（`-DVM_GUEST_ARM64 -DVM_REG_COUNT=35`）执行，逐寄存器 + 标志位比对。

做法：用 **x86-64 宿主 blob** 承载 **arm64 客户机字节码**（`vmpbuild -guest arm64`），
因此不需要 aarch64 工具链也能验证客户机语义。命令见 `docs/RUNBOOK.md` 4.5。

**仍需 CI/真机**：ARM64 宿主 blob 构建（Windows/arm64、Linux/arm64）与 Linux/arm64 的 qemu 端到端。

## 4. 未达标项与已知问题（如实列出）

1. **解释器用 `-O1` 编译**：`-O2` 下，只要浮点函数里含**整数↔浮点转换**，**整个解释器**会被 gcc 编译错
   （连不执行浮点的 `check_key` 都算错）。已二分到触发点，但**根因未定位**（疑为解释器里既有 UB）。
   代价已实测（第 79 轮复测）：`check_key` protected **50 ns/iter**、`sum_to` **1100 ns/iter**；与 -O2 时代的 35/700 相比约 1.4–1.6×。
2. **`fp_mix` 的两个大参数**取值仍与原生不符（未定位），因此没有进 E2E 用例清单。
3. **调用约定只覆盖整数参数/返回值**（浮点/向量参数不进出宿主）；浮点只在被保护函数内部可用。
4. **ELF 共享库的运行时 `dlopen` 验证**缺失（定位逻辑已打通，需 Linux 执行）。
5. **CI 未实跑**：`ci.yml` 的四个作业都已写好并通过静态校对（路径存在性、`bash -n`），但从未真正运行过。
6. `docs/STATUS.md` 的**第 52–57 轮条目已丢失**（我在第 75 轮做整文件重排时被读取上限截断所致），
   第 58–75 轮只有要点补记；完整细节仍在会话记录中。

## 5. 怎么把 ⑤ 真正闭环（建议路径）

1. 把 `D:\vmp-x` 推到一个 GitHub 仓库（目前**不是 git 仓库**，也没有 `.gitignore`→ 已补上）；
2. 启用 `.github/workflows/ci.yml`，四个作业会分别回答：
   - `windows-amd64`：x86-64 E2E（146 例）+ DLL E2E（3 例）—— 预期通过；
   - `linux-amd64`：`tools/e2e.sh`（含「不得有 W+X 段」断言）—— **首次运行最可能暴露问题**（脚本从未在 Linux 上跑过）；
   - `linux-arm64`：`tools/e2e_arm64.sh`（aarch64 交叉工具链 + qemu-user）—— 同样首次运行；
   - `arm64-guest-differential`：ARM64 客户机语义（本机已通过；CI 侧用的是 linux/amd64 宿主 stub 的等价配方，尚未实跑）；
   - `windows-arm64-blob`：Windows/arm64 blob 构建 —— 需要一个能产出 aarch64 **COFF** 的编译器，CI 镜像可能没有；
     该作业会**明确失败**并指出缺哪个工具（设计上不允许静默跳过）。
3. 把 CI 的真实输出贴回来，我按结果修（这是唯一能闭环 ⑤ 的方式）。

## 8. CI 实跑结果与最终判定（本轮更新）

四个作业都已有**明确结论**（仓库已公开，运行与注解可直接匿名阅读）：

| 作业 | 结论 |
|---|---|
| `windows-amd64` | **success**（runner 上无失败步骤）：146 例 x86-64 E2E、3 例 DLL、ARM64 客户机差分、Linux 载荷 —— 全部在 runner 上通过。第 96 轮修掉了 runner 上唯一失败项 `mt`（并发用例）的真因：多余的「兜底缓冲池」在 4 线程 × 嵌套下被耗尽 |
| `linux-amd64` | **全绿**（CI `failedSteps=[]`）：打包 ✓、**无 W+X** ✓、payload 探针 ✓、差分 E2E ✓。根因（重叠 PT_LOAD 的映射顺序导致 `.bss` 被 RX 覆盖）已修 |
| `linux-arm64` | blob 构建 ✓、AArch64 打包 ✓（8 字节 `mov x16,x30 ; b thunk`）、**qemu 首次真正执行** → 段错误（未定位）；另有 payload 段退回 RWX 的缺口 |
| `windows-arm64-blob` | 需要能产出 aarch64 COFF 的编译器，runner 镜像没有 —— 外部缺口（作业显式失败） |

### 对原目标 ⑤（arm64 执行验证 + CI 实跑）的判定

- **已达成**：CI 矩阵实跑（四个作业都在真实 runner 上跑过，且四个结论都可读）；ARM64 **客户机**语义链在真实差分中验证并纳入门禁；
  ARM64 **宿主** blob 从『从未构建过』到『能构建、能打包、能被 qemu 执行』；
- **未达成**：ARM64 宿主 blob 的执行结果还是段错误，Linux/amd64 的差分也还没全绿 —— 这两条都是**已定位或已收窄**的问题，
  但需要继续修（不是环境缺失）；
- 结论：⑤ 从『完全受限』推进到『可在 CI 上闭环』，但**尚未完成**。

### 这一路修掉的真缺陷（值得单独列出）

1. **ELF 的 PC 相对重定位多加了 4 字节**（COFF 需要、ELF 不需要）—— 这是 Linux 侧 SIGILL 的真根因；
2. AArch64 宿主 blob 的两处编译问题（`VM_SAVE_*` 常量守卫、共享头的 `-I` 路径）；
3. aarch64 的 `__aarch64_swp4_acq` 助手缺失（`-mno-outline-atomics`）；
4. AArch64 的 ADRP/ADD 重定位从未支持；
5. 内置合并器把 AArch64 映射符号 `$x` 当重复定义；同一个 `.c` 被编译两次导致全局符号重复；
6. ELF 目标里的 `SHT_NOBITS`（.bss）读取报错、`vm_entry` 偏移为 0 被误判为坏值。
7. **重叠 `PT_LOAD` 的映射顺序**：内核按程序头表顺序 mmap，重叠区间上后者覆盖前者 —— 可写覆盖段若排在 payload 段之前，`.bss` 会被 RX 映射盖回只读，解释器写解密缓存即 `SIGSEGV/SEGV_ACCERR`（PE 侧不暴露）。这是 `linux-amd64` 长期红着的真根因。


## 9. 最终判定（第 108 轮：CI 全矩阵实跑后的结论）

| 作业 | 结论 |
|---|---|
| `windows-amd64` | **success**（持续）：146 例 x86-64 E2E、3 例 DLL、ARM64 客户机差分、Linux 载荷在本机执行 —— 全部在 runner 上通过 |
| `linux-amd64` | **success**：blob 构建 ✓、打包 ✓、readelf 无 W+X 断言 ✓、payload 探针 ✓、差分 E2E ✓。长期红着的根因是**重叠 PT_LOAD 的映射顺序**（可写 .bss 覆盖段被 payload 的 RX 映射盖回只读 → SEGV_ACCERR） |
| `linux-arm64` | blob 构建 ✓（含 `-mno-outline-atomics`、共享头 `-I` 路径、aarch64 保存布局常量）、AArch64 打包 ✓（8 字节 `mov x16,x30 ; b thunk`，已用反汇编核实）、**qemu 能执行** ✓；修掉两个宿主 stub bug（寄存器还原、标志位换算）后不再崩溃，但**每个被保护函数返回 0**，尚未算对 |
| `windows-arm64-blob` | **外部缺口**：runner 镜像里没有能产出 aarch64 COFF 的编译器，作业按设计显式失败（不是回归） |

### 对原目标 ⑤（arm64 执行验证 + CI 实跑）的判定

- **已达成**：CI 矩阵**真实实跑**且四个作业的结论都可匿名阅读；ARM64 **客户机**语义链由真实差分验证并纳入本机门禁；
  ARM64 **宿主** blob 从「从未构建」推进到「能构建、能打包、能被 qemu 执行」；x86-64 的 ELF 路径（此前在 Linux 上从未真正执行过）**已全绿**——
  包括独立的 payload 探针与端到端差分；
- **未达成**：ARM64 宿主 blob 的执行仍未算对（返回 0，正在用 payload 探针二分）；`windows-arm64-blob` 受限于镜像里没有 aarch64 COFF 编译器；
- **结论**：⑤ 从「受环境所限」推进到「可在 CI 上闭环验证」，只剩一个运行期缺陷与一个外部工具链缺口。

### 这条路上修掉的真缺陷（累计 8 条）

1. ELF 的 PC 相对重定位多加了 4 字节（COFF 需要、ELF 不需要）—— Linux 侧 SIGILL 的真根因；
2. AArch64 宿主 blob 的两处编译问题（`VM_SAVE_*` 常量守卫、共享头 `-I` 路径）；
3. aarch64 的 `__aarch64_swp4_acq` 助手缺失（`-mno-outline-atomics`）；
4. AArch64 的 ADRP/ADD 重定位从未支持；
5. 内置合并器把 AArch64 映射符号 `$x` 当重复定义；同一份 `.c` 被编两次导致全局符号重复；
6. ELF 目标里的 `SHT_NOBITS`（.bss）读取报错、`vm_entry` 偏移为 0 被误判；
7. **重叠 `PT_LOAD` 的映射顺序**（可写覆盖段必须排在 payload 段之后）—— linux-amd64 长期红着的真根因；
8. **arm64 入口 stub 的两处**：从一块从未写过的保存区还原 X1..X29；标志位换算 `lsr #28` / 多余的 `rbit`。
