# PE32（32 位 x86 客户机）支持：现状、证据、决策

> 这份文档是**评审用**的：Go 侧已落地的部分、卡点的确切原因、三条路的确切命令与代价。
> 逐项证据编号指向 `docs/STATUS.md`。

## 一句话结论

**Go 侧（解析 → 32 位解码 → 32 位 lift → 客户机栈语义 → 逐函数预检）已经落地并有实测证据** ✓；
把 blob 注入**真实 PE32 进程**需要 **32 位 blob**（thunk/trampoline 是 per-platform 汇编），
而这需要一台带 **32 位 C 工具链**的机器 —— 本机没有（`gcc -m32` 失败、无 clang）。**等你拍板。**

## 已完成（逐项可查）

| 能力 | 证据 |
|---|---|
| PE32 **解析**（`internal/load/pe` 支持 PE32/PE32+ 双分支；`ImageBase` 宽度/偏移按格式走） | #423；真实样本 `C:\Windows\SysWOW64\notepad.exe` → `base=0x400000 entry=0x25FF0 sections=6` |
| 解码层 **32 位模式**（`DecodeMode`/`DecodeRangeMode`；`0x40-0x4F` 是 INC/DEC 而非 REX、`push` 宽度、`[disp32]` 是**绝对地址**而非 RIP-relative） | #424；4 条断言（含"两种模式结果必须不同"） |
| lifter **32 位模式接线** + **地址/指针宽度按模式** | #425 / #426 |
| **栈槽与栈传参记账**（`push`/`pop` 按模式记 4/8 字节；32 位参数在 `[esp+4]` 而非 `[rsp+8]`） | #431；`push 42; mov eax,[esp+4]` → 32 位 `Disp=0x44` / 64 位 `0x4` |
| **客户机 x86-32 模式**（C 解释器 + Go 参考：栈槽 4 字节；`PUSH_R` 与 `PUSH_I` 两条路径） | #428 / #432；`C(x86-64)=8 C(x86-32)=4 Go(GuestX86)=8 Go(GuestX8632)=4` |
| 上述差分**已进 CI 门禁**（`guest differential (arm64 + x86-32)`，门禁数仍 11） | #432 |
| **真实 32 位代码**验证 | #433；notepad 三处各连解 24 条全对齐；入口翻译走到 +0x14F2 后止于数据 |
| **逐函数可保护性预检**（`-mode 32` + 免符号表 `-rva/-len`） | #435 |

## 今天就能用：预检一个 32 位函数能不能保护

```powershell
# 从客户的 PDB 取到函数的 RVA 与 size（他们的 verify.py 已用 dbghelp 枚举符号）
build\vmp-lift.exe -exe <pe32> -rva 0x<rva> -len <size> -mode 32 -out build\one.vmb
```

- 成功：打印 `-> N IR -> M bytecode bytes`；
- 失败：`[!] at +0x..: <原因>` 并 **exit 1**（例如 `unknown opcode 0x6B`、`unrecognized instruction`）—— 这就是"缺哪条指令"；
- **务必传对的 `-len`**：`-rva` 模式没有符号表，走出函数体就会撞数据而**误报** ✗。

## 卡点：为什么必须有 32 位 blob

受保护的产物是一个**进程内的注入体**：目标进程是 32 位，注入的 blob 就必须是 **32 位机器码**（入口蹦床 `vm_entry`、
native 调用蹦床、以及 ctx 布局都由平台决定）。现有 blob 平台只有 `stub/win/{x64,arm64}`、`stub/linux/{amd64,arm64}` —— 没有 32 位。

本机实测：`gcc -m32` **失败**（ucrt64 只有 64 位，`ld` 跳过不兼容的 `libmingw32.a`）；**没有 clang**；
msys2 的 `pacman` **在**（`C:\msys64\usr\bin\pacman.exe`）。

| 路 | 确切做法 | 代价 | 本地可验证 |

**建议**：32 位是**真实客户需求** ⇒ **A**；只是"顺手提到" ⇒ **C**。
## 【已选 A】工具链就绪 + 移植面实测（本轮）

- 第一次失败的真因：**残留的数据库锁** `C:\msys64\var\lib\pacman\db.lck`（错误信息自己指出可删）—— 不是网络问题；

- 装好后 `i686-w64-mingw32-gcc.exe` 是 **15.1.0** ✓；注意**必须把 `C:\msys64\mingw32\bin` 加进 PATH**，
  否则它找不到内部的 `cc1`/`as`（症状：`compile rc=1` 但几乎看不到报错）。
- 实测能出 32 位代码：编出的目标文件 `machine=0x014C` ✓（i386）。

**移植面实测（用 `vmpbuild -cc i686-w64-mingw32-gcc.exe -src stub/win/x64 -guest x86-32` 直接探）**

```
vm_interp.c:18   error: size of array 'vm_sa_ctx_size' is negative   ← 32 位 ctx 布局的静态断言
vm_interp.c:154  error: expected expression before '__int128'        ← 宏里的 128 位字面量
vm_interp.c:262  error: '__int128' is not supported on this target  ← 核心：i686 没有 128 位整型
vm_interp.c:285  error: '__int128' is not supported on this target
```

⇒ 32 位 blob 的**工作清单**（按依赖顺序）：
1. **`__int128` 降级**：i686 没有 128 位整型 ⇒ 128 位乘/除要走可移植实现。**已有先例**：
   早年为了 aarch64 CI 已经把除法写成"u64/i64 + 可移植长除法"（不用 `__int128` 除法）；乘法那几处照同样办法处理即可。
2. **ctx 布局**：`vm_abi.h`/`vm_types.h` 里的偏移是**指针宽度相关**的（32 位下 4 字节）⇒ 静态断言要按平台给期望值；
3. **入口蹦床**：`vm_entry_asm.S` 是 64 位 AT&T 汇编 ⇒ 需要 32 位版本（`stub/win/x86/vm_entry_asm.S`）；
4. **native 调用蹦床**：`vm_calln_x64`（Win64 ABI：RCX/RDX/R8/R9 + xmm0-3）⇒ 32 位要按 **cdecl** 走栈 + 无 xmm；
5. **其余平台文件**：`vm_abi.h` / `blob_probe.c` 的 32 位变体 + `vmpbuild`/`vmpack` 的平台与 `Arch` 分支。


## 若选 C：仓库里该保留什么

- 上面"已完成"的全部能力**都保留**：它们在门禁覆盖内、不增加维护负担，而且是将来重启 PE32 的地基；
- **保持** `vmpack` 对 PE32 的**明确拒绝 + 可操作提示**（绝不为兼容而静默产出坏产物）；
- 可以删的是：`stub/win/x64` 里那段 `VM_GUEST_X86_32` 的 C 侧分支吗？**不建议** —— 它是"客户机 x86-32"的唯一实现，
  且已被门禁覆盖（删了等于丢掉已验证的资产）。

## 仍未做（不论选 A/B/C 都要知道）

1. **入口 ABI**：32 位下参数在客户机栈上，而 `vm_calln_x64` 蹦床按 **x64 ABI** 传 `RCX/RDX/R8/R9` —— 跨到 native 调用时需按 32 位 ABI 走栈；
2. **PE32 注入**：`internal/inject` 目前只按 AMD64/ARM64 布局写（节表、重定位、入口补丁都要 32 位变体）；
3. **32 位 harness**（`blob_probe.c` 的 32 位构建）与 32 位 CI 作业；
4. **批量预检**：一次列出整个 exe 所有函数的可保护性 —— 需要 PDB 解析（客户的 `demo32.exe` 既无 MAP 也无 COFF 符号表）。

### 更新（目标达成）：32 位 blob 已在 32 位 harness 上跑通真实函数

结论：**⑥ 达成**。证据与细节见 `docs/STATUS.md` #453；两个真实函数（i686 gcc 编的 32 位 exe）
在 i686 blob 里的返回值与原生**完全一致**：

    v:32_sum10 (原生 55)  -> rax=55  rc=1        与 x64 宿主侧逐字一致 ✓
    v:32_loop  (原生 165) -> rax=165 rc=0        x64 宿主的 x86-32 客户机模式反而跑不了（rc=99，既有缺口）

构建命令（三条，均为仓库约定或本目标新增）：

    # 1) i686 blob（恒等操作码，便于用 vmp-lift 的默认映射做端到端验证）
    build/vmpbuild.exe -cc i686-w64-mingw32-gcc.exe -src stub/win/x86 \
        -out build/vm_x86_id.bin -manifest build/vm_x86_id.json \
        -entry vm_entry -guest x86-32 -merge go -random-opcodes=false

    # 2) 32 位 harness（必须是 i686 进程：i686 blob 只能被 32 位进程加载）
    i686-w64-mingw32-gcc -O2 -Wall -I stub/win/x86 -I stub/win/x64 \
        -o build/runbc_i686.exe stub/win/x64/blob_probe.c

    # 3) 真 32 位被测函数（不是合成用例）
    i686-w64-mingw32-gcc -O0 -o build/real32b.exe build/real32b.c
    build/vmp-lift.exe -exe build/real32b.exe -rva 0x1500 -len 49 -mode 32 \
        -manifest build/vm_x86_id.json -out build/real32b.vmb
    build/runbc_i686.exe build/vm_x86_id.bin <vm_run偏移> build/real32b.vmb 0 <vm_reloc_tab偏移>

注意：`-len` 必须是**函数真实长度**（用 `nm` 的相邻符号差算，例如 `vm32_loop` 到 `main` = 49 字节）；
给短了会翻译出残缺字节码、给出无意义的结果。

### 踩过的关键坑（按时间顺序，均有 STATUS 条目）

1. **描述符字段掩码**：`-no-encrypt` 时打包端不加掩码，而运行期**总是**按掩码解 ⇒ 字段全垃圾（#463 修）；
2. **校验表掩码**：同一条件的第二处 ⇒ `delta` 成垃圾 ⇒ 野指针崩在 `vm_patch_mac`（#464 修）；
3. **i686 蹦床用 `movl` 填 u64 寄存器槽** ⇒ 高半部是栈垃圾 ⇒ 无符号栈守卫误判 ⇒ 错值（#473 修）。
