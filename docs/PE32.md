# PE32（32 位 x86 客户机）支持：现状、证据、决策

> 这份文档是**评审用**的：Go 侧已落地的部分、卡点的确切原因、三条路的确切命令与代价。
> 逐项证据编号指向 `docs/STATUS.md`。

## 一句话结论

**Go 侧（解析 → 32 位解码 → 32 位 lift → 客户机栈语义 → 逐函数预检）已经落地并有实测证据** ✓；
把 blob 注入**真实 PE32 进程**需要 **32 位 blob**（thunk/trampoline 是 per-platform 汇编），
而这需要一台带 **32 位 C 工具链**的机器 —— 本机没有（`gcc -m32` 失败、无 clang）。**等你拍板。**

## 已完成（逐项可查）

| 能力 | 证据 |
|---|---|
| PE32 **解析**（`internal/load/pe` 支持 PE32/PE32+ 双分支；`ImageBase` 宽度/偏移按格式走） | #423；真实样本 `C:\Windows\SysWOW64\notepad.exe` → `base=0x400000 entry=0x25FF0 sections=6` |
| 解码层 **32 位模式**（`DecodeMode`/`DecodeRangeMode`；`0x40-0x4F` 是 INC/DEC 而非 REX、`push` 宽度、`[disp32]` 是**绝对地址**而非 RIP-relative） | #424；4 条断言（含"两种模式结果必须不同"） |
| lifter **32 位模式接线** + **地址/指针宽度按模式** | #425 / #426 |
| **栈槽与栈传参记账**（`push`/`pop` 按模式记 4/8 字节；32 位参数在 `[esp+4]` 而非 `[rsp+8]`） | #431；`push 42; mov eax,[esp+4]` → 32 位 `Disp=0x44` / 64 位 `0x4` |
| **客户机 x86-32 模式**（C 解释器 + Go 参考：栈槽 4 字节；`PUSH_R` 与 `PUSH_I` 两条路径） | #428 / #432；`C(x86-64)=8 C(x86-32)=4 Go(GuestX86)=8 Go(GuestX8632)=4` |
| 上述差分**已进 CI 门禁**（`guest differential (arm64 + x86-32)`，门禁数仍 11） | #432 |
| **真实 32 位代码**验证 | #433；notepad 三处各连解 24 条全对齐；入口翻译走到 +0x14F2 后止于数据 |
| **逐函数可保护性预检**（`-mode 32` + 免符号表 `-rva/-len`） | #435 |

## 今天就能用：预检一个 32 位函数能不能保护

```powershell
# 从客户的 PDB 取到函数的 RVA 与 size（他们的 verify.py 已用 dbghelp 枚举符号）
build\vmp-lift.exe -exe <pe32> -rva 0x<rva> -len <size> -mode 32 -out build\one.vmb
```

- 成功：打印 `-> N IR -> M bytecode bytes`；
- 失败：`[!] at +0x..: <原因>` 并 **exit 1**（例如 `unknown opcode 0x6B`、`unrecognized instruction`）—— 这就是"缺哪条指令"；
- **务必传对的 `-len`**：`-rva` 模式没有符号表，走出函数体就会撞数据而**误报** ✗。

## 卡点：为什么必须有 32 位 blob

受保护的产物是一个**进程内的注入体**：目标进程是 32 位，注入的 blob 就必须是 **32 位机器码**（入口蹦床 `vm_entry`、
native 调用蹦床、以及 ctx 布局都由平台决定）。现有 blob 平台只有 `stub/win/{x64,arm64}`、`stub/linux/{amd64,arm64}` —— 没有 32 位。

本机实测：`gcc -m32` **失败**（ucrt64 只有 64 位，`ld` 跳过不兼容的 `libmingw32.a`）；**没有 clang**；
msys2 的 `pacman` **在**（`C:\msys64\usr\bin\pacman.exe`）。

## 三条路（含确切做法与代价）

| 路 | 确切做法 | 代价 | 本地可验证 |
|---|---|---|---|
| **A** | `C:\msys64\usr\bin\pacman.exe -S mingw-w64-i686-gcc`（如需再补 i686 头文件），之后 `stub/win/x86` 用 i686 gcc 编 | 联网装工具链、**改机器** | ✅ 可以（推荐） |
| **B** | 只在 CI 用 clang：`clang --target=i686-pc-windows-msvc -c ...`（freestanding，不需要 32 位 libc/头文件）+ `vmpbuild -merge go` 合并 | 不改本机；本地无法端到端验证 | ❌ 只能靠 CI 迭代（每轮约 5 分钟） |
| **C** | PE32 到此为止，保持"明确拒绝 + 可操作提示"，预算回 PE64 | 客户的 `demo32.exe` 继续被拒 | — |

**建议**：32 位是**真实客户需求** ⇒ **A**；只是"顺手提到" ⇒ **C**。

## 若选 C：仓库里该保留什么

- 上面"已完成"的全部能力**都保留**：它们在门禁覆盖内、不增加维护负担，而且是将来重启 PE32 的地基；
- **保持** `vmpack` 对 PE32 的**明确拒绝 + 可操作提示**（绝不为兼容而静默产出坏产物）；
- 可以删的是：`stub/win/x64` 里那段 `VM_GUEST_X86_32` 的 C 侧分支吗？**不建议** —— 它是"客户机 x86-32"的唯一实现，
  且已被门禁覆盖（删了等于丢掉已验证的资产）。

## 仍未做（不论选 A/B/C 都要知道）

1. **入口 ABI**：32 位下参数在客户机栈上，而 `vm_calln_x64` 蹦床按 **x64 ABI** 传 `RCX/RDX/R8/R9` —— 跨到 native 调用时需按 32 位 ABI 走栈；
2. **PE32 注入**：`internal/inject` 目前只按 AMD64/ARM64 布局写（节表、重定位、入口补丁都要 32 位变体）；
3. **32 位 harness**（`blob_probe.c` 的 32 位构建）与 32 位 CI 作业；
4. **批量预检**：一次列出整个 exe 所有函数的可保护性 —— 需要 PDB 解析（客户的 `demo32.exe` 既无 MAP 也无 COFF 符号表）。
